# ADR 0003: กันจองซ้อนด้วย row lock และ ExclusionConstraint

- **สถานะ:** ใช้อยู่
- **วันที่:** ตุลาคม 2026 (Sprint 2)

## บริบท

ห้องเดียวกันห้ามมีแขกสองกลุ่มในคืนเดียวกัน แต่มีหลายทางที่อาจชนกันพร้อมกัน:
แขกหลายคนจองห้องสุดท้ายพร้อมกัน, แขกกดยืนยันซ้ำ, พนักงานลากย้ายห้องใน Tape Chart
และพนักงานเปลี่ยนห้องตอนเช็คอิน การตรวจว่าห้องว่างใน Python อย่างเดียวไม่พอ
เพราะสอง request อ่านพร้อมกันแล้วเห็นว่าว่างทั้งคู่ได้

## การตัดสินใจ

ป้องกันสองชั้น:

1. **ชั้น service:** ทุกการจองหรือย้ายห้องทำใน `transaction.atomic()` และล็อกแถวที่เกี่ยวข้องด้วย `select_for_update()`
   เรียงตาม primary key เพื่อไม่ให้ deadlock
   - **สร้างการจอง** (`create_booking()`): ยังไม่มีแถว Booking ให้ล็อก จึงล็อก RoomType ที่ขอจอง
     แล้วตรวจห้องว่างและเลือกห้องให้อัตโนมัติ
   - **ย้ายห้องใน Tape Chart, เช็คอิน, เช็คเอาต์:** ล็อกตามลำดับ Booking → BookingRoom → Room
2. **ชั้นฐานข้อมูล (ด่านสุดท้าย):** `BookingRoom.stay_range` เป็น `daterange` แบบ `[check_in, check_out)`
   และมี `ExclusionConstraint` ชื่อ `bookings_bookingroom_no_overlap` (`room` เท่ากัน และ `stay_range` ทับกัน ห้ามมี)
   มีผลเฉพาะแถวที่ `is_active=True` การจองที่ยกเลิกหรือปล่อยห้องแล้วจึงไม่กันห้อง
   ถ้าการตรวจในชั้นแรกพลาด ฐานข้อมูลจะปฏิเสธ service จับ `IntegrityError` ใน savepoint แล้วตอบเป็นข้อความภาษาไทย

นอกจากนี้ การจองมี `idempotency_key` (unique ต่อโรงแรม) ทำให้กดส่งซ้ำได้การจองเดิม ไม่ใช่การจองใหม่

## ผลที่ตามมา

- **ดี:** ทดสอบจริงบน PostgreSQL ใน CI: เทสต์ `apps/bookings/tests/test_concurrency.py` ส่ง 50 คำขอพร้อมกันเพื่อจองห้องสุดท้าย
  สำเร็จ 1 รายการ อีก 49 ได้ข้อความว่าห้องเต็ม (TECH-07)
- **ดี:** ทุกทางที่เปลี่ยนห้อง (จอง, Tape Chart, เช็คอิน) ได้การป้องกันเดียวกันจาก constraint โดยไม่ต้องเขียนซ้ำ
- **ข้อเสีย:** ผูกกับ PostgreSQL (`btree_gist`, `DateRangeField`) ใช้ SQLite ไม่ได้ ทั้ง dev, CI และ production จึงใช้ PostgreSQL 16
- **ข้อจำกัด:** constraint ดูแค่ช่วงวันที่ ไม่ได้ดูว่าแขกคนก่อนเช็คเอาต์ไปแล้วจริงหรือยัง
  การจองที่ต่อกันพอดี (คนหนึ่งออก อีกคนเข้าวันเดียวกัน) จึงผ่าน constraint ได้ การกันเช็คอินซ้อนในวันนั้นเป็นหน้าที่ของ service เช็คอิน
  (ปฏิเสธเมื่อแขกคนก่อนยังพักอยู่ในห้อง เพิ่มใน #190)
